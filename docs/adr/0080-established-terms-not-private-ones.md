## やさしい説明

agent が、自分たちにしか通じない言葉を作らないようにする。
特別な言葉が要るときは、業界や open source ですでに使われている言葉を使う。
どうしても新しい言葉が要るときは、その場で人に相談する。
日本語の文の中で、英語と日本語のどちらで書くか迷う言葉は、英語のまま書く。

## Context

- 2026-11-18 03:18 JST に、所有者が全エージェント共通の指示の更新を指示した。指示の中に用語集や用語についての記載があれば、次で上書きする。
    1. プライベートな独自の用語を使わない。
    2. 特殊な用語は、既存の業界の用語か open source で使われている用語を使う。プライベートな用語を定義したい場合は、その場で相談する。
    3. 決める用語が大量にある場合や、作ろうとしているものが独自の領域である場合は、最初に用語集を作る skill を探し、より良い用語と定義にする。
- 同じ日の 03:21 JST に、4 つ目を加えた。英語と日本語のどちらを使うか用語ごとに迷った場合は、英語を基本にする。造語、カタカナ語、日本語で無理に表す言葉遣いは避ける。日本語と通常の英語の用語が混ざるのはよい。
- 全エージェント共通の指示（`ROOT_AGENTS.md`、`ROOT_CLAUDE.md`、spoke）に、用語集の節は無かった（`rg` で確認）。用語に触れていたのは次の 3 か所で、どれも 4 点と矛盾しない。
    - hub の「Name things specifically」: その領域で何をするかを言う名前を選ぶ。
    - spoke `naming.md`: 領域の言葉で 1 文にしてから名前を取る。同じ概念には同じ名前を使う。
    - spoke `plain-language.md`: 専門用語は最初に説明する。1 つのものに 1 つの語。日本語では、平易な語があるなら漢語とカタカナ語より平易な語を使う。
- `plain-language.md` の「漢語とカタカナ語より平易な語」は、一般の語（動詞など）についての規則である。4 つ目は専門用語についての規則で、対象が違う。
- 用語集に関わる skill は 4 つが宣言済みである（`dump/harness/skill-lock.json`）: `domain-modeling`、`ubiquitous-language`、`provable-glossary`、`find-skills`。指示が名指しする skill は宣言済みでなければならない（`tests/unit/test_named_skills_declared.py`）。
- hub（常に読まれる指示）の箇条書きは 32 個で、上限は 40 個である。

## Decision

A 案の次の 7 項を、必須事項（MUST）として採択する。

- D1: agent は、独自の用語（この team、この repo、この session だけが使う語や、語の新しい意味）を作ってはならない。
- D2: 概念を表す用語は、業界か open source ですでに使われているものから取らなければならない。探す先は、標準や RFC、言語・framework・protocol の文書、広く使われている open source の project とする。
- D3: 合う用語が無いときは、その用語を code、ファイル名、文書に入れる前に、その場で人に相談しなければならない。概念、確かめた既存の用語とそれが合わない理由、提案する用語を示す。人が同意してから使い、最初に出る所で定義する。
- D4: 決める用語が多いとき、または作るものが独自の領域であるときは、用語を 1 つずつ決める前に、用語集の skill を探して使わなければならない。
- D5: 日本語の文の中で、用語を英語と日本語のどちらで書くか迷ったら、英語で書かなければならない。造語、カタカナの音写、無理な日本語の言い換えにしてはならない。日本語の文に通常の英語の用語が混ざるのはよい。
- D6: すでに repo にある用語も例外にしない。従ってよいのは、確立した用語か、人が承認した用語（用語集か ADR に記録がある）だけとする。承認の無い独自の用語を見つけたら、その場で人に相談し、新しい名前、文書、回答に広げてはならない。既存の識別子と API は、人が決めるまで変えない。
- D7: これらは spoke `naming.md` の節に書き、hub は既存の「Name things specifically」の項目に文を足す（箇条書きは増やさない）。`plain-language.md` は、一般の語と専門用語の規則を分けて書く。テスト（`tests/unit/test_established_terms_guidance.py`）が規則の文を保つ。

## Options Considered

| 案 | 利点 | コスト・リスク | 裁定 |
| --- | --- | --- | --- |
| A) `naming.md` に節を足し、hub の既存の項目に文を足す（本案） | 名前と用語の規則が 1 か所にまとまる。hub の箇条書きが増えない。名前を付けない作業（文書、計画）でも、hub の文で規則が届く | hub の 1 項目が長くなる | 所有者が採択 |
| B) 新しい spoke `terminology.md` を作る | 節が独立する | `naming.md` の「領域の言葉で名付ける」「同じ概念に同じ名前」と内容が重なり、2 か所を読むことになる | 却下: 同じ知識が 2 か所に分かれる |
| C) hub に 4 つの箇条書きを足す | 常に読まれる | 箇条書きが 36 個になり、上限 40 に近づく。例と手順を書く場所が無い | 却下: hub が長くなる |
| D) spoke にだけ書き、hub は変えない | hub が変わらない | spoke は「名前を付けるとき」にしか開かれない。文書や回答の中で用語を作るときに、規則が読まれない | 却下: 規則が届かない場面がある |

## Consequences

- **Positive**: 新しく読む人と agent が、調べれば分かる言葉で code と文書を読める。新しい用語は、人が同意したものだけになる。日本語の文書で、同じ概念に英語、カタカナ語、訳語が混ざらなくなる。
- **Negative**:
    - 合う用語が無いたびに、agent の作業が人への相談で止まる。
    - 「確立した用語か」「迷うか」の判断は agent に任され、機械的な検査は無い。テストが保つのは指示の文だけである。
    - 日本語の文書に英語の用語が増える。英語の用語に慣れない読み手には読みにくくなる。
- **Neutral**: 既存の識別子と API は、この ADR では改名しない（D6）。Claude 用の overlay の「ASCII の図の凡例に日本語の注を付ける」規則は変えない。注は用語の説明であって、用語の置き換えではない。

## 他の DR との照合

0001〜0079 の 78 件（0046 は欠番）の題名と状態を走査し、用語、用語集、glossary、naming、命名、日本語、カタカナで全文を検索した。当たった記録と、指示の構成を決めた 0052、skill の宣言を決めた 0043 を読んだ。PDR はない。

- **矛盾**: 見つからなかった。0052 の Decision 6（具体的な命名）と 7（Plain Language）に、本案は用語の出どころと言語の選び方を足す。0052 の決定は変えない。
- **重複**: 番号 0080 は未使用。同じ決定の記録はない。
- **誤読**: 0052 の Plain Language は「ふつうの語を使う」と決めている。本案の D5 は専門用語だけを対象にし、一般の語を英語にすることは求めない。
- **偽の関連**: 0051（決裁待ち一覧）の「やさしい説明」や日本語を先にする書き方は、DR の書き方の規則で、agent が code と文書で使う用語の規則ではない。
- **関係誤認**: 0043 は skill の入れ方を決めている。本案は宣言済みの skill を名指しするだけで、入れ方は変えない。
